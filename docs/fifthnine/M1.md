## Discovery rules

Walk order is sorted by name. Never followed: symlinks (inside the repo: skipped as `ignored`; pointing outside: `symlink_outside_root`). Built-in excluded directories: `.git .hg .svn node_modules .venv venv __pycache__ .tox .nox .mypy_cache .pytest_cache .ruff_cache .gradle .idea .vscode target build dist .terraform vendor site-packages .eggs`, plus any directory containing `pyvenv.cfg` (a virtualenv under any name). Names such as `env` are deliberately not excluded because teams keep per-environment manifests there. Consequence: anything a team keeps under those names (for example Kubernetes YAML in a `build/` directory) is not inventoried; the coverage section lists the excluded directories. The root `.gitignore` and `.fifthnine.yml` `ignore_paths` apply with gitignore semantics; nested `.gitignore` files are not read in v0.1. A `.gitignore` line that is not a valid pattern is skipped and reported (`COV-IGNORED-CONFIG`); an invalid `ignore_paths` entry is a configuration error (exit 2). Files and directories excluded by either are counted under `COV-IGNORED`. File names that are not valid UTF-8 are skipped as unsupported. The report file named by `--output` is never inventoried, so writing it inside the repository does not change the next scan. Files FifthNine parses are capped at 1 MiB (`--max-file-size`) and checked for NUL bytes; other files are only counted. The walk stops at 20,000 files with a blocking coverage notice.

## Detection rules and limits

Values come from parsers. Line numbers come from the XML and YAML parsers. For TOML and requirements files the line is found by searching for the parsed key inside the section the value came from (`[project]`, `[tool.poetry.dependencies]`, `[versions]`, each `[[package]]` block of a lockfile), skipping comment lines. When the same component version is found in several files, one entry is kept: lockfile first, then build descriptor, then Dockerfile. Different versions of the same component are all kept.

- Maven: `${property}` resolved one level from the same POM only. Parent POM inheritance, profiles and `${revision}` from CI flags are not resolved; the version is reported as not determined.
- Requirements files: `\` continuations are joined, comments and `--hash` options removed, option lines (`-r`, `-e`, `--index-url`) skipped. A line that names a tracked component but is not a valid requirement (a URL or VCS reference) is listed as version not determined.
- Gradle: literals only, with `//` and `/* */` comments removed first. `jvmToolchain(N)`, `JavaVersion.VERSION_1_8` and Kotlin `id(...).version(...)` are read. Version catalogs (`libs.versions.toml`) are read. Values computed in Groovy or Kotlin DSL, `buildSrc` and settings plugin management are reported as not determined.
- Python: exact pins (`==`) and lockfiles only. A range such as `fastapi>=0.110` without a lockfile gives "version not determined", never a guessed version. `requires-python` is not treated as the runtime version.
- Spring Framework is reported only when declared explicitly; the Boot-managed version is not inferred in M1.
- Version qualifiers such as `2.3.4.RELEASE`, `4.0.0-SNAPSHOT` and `3.4.0-M1` are compared by their numeric part; a version with no numeric part is reported with `FN-OPS-002` and never classified as in range.
- Dockerfile image digests are ignored; a major-only tag such as `python:3` is version not determined.
- Kubernetes: only YAML files with top-level `apiVersion` and `kind` keys are parsed; other YAML (OpenAPI specs, CI files, Compose) is counted, not parsed. Every object's `apiVersion`/`kind` is inventoried. Items inside `kind: List` are not inventoried in v0.1. Kinds v0.1 reads are listed in the stack; other workload kinds (StatefulSet, DaemonSet, Job, CronJob, Pod, ReplicaSet, Argo Rollout) are listed as unsupported; non-workload kinds appear only in facts.
- Helm templates are detected by template syntax and skipped; Kustomize overlays are detected and not built (E3).
- Java, Kotlin and Python source files are counted, not parsed. Spring configuration files are inventoried; profile resolution starts in M2.

## Untrusted input

Parsers never construct objects from repository content. XML refuses DOCTYPE and entity declarations. YAML anchors reused as aliases are refused in `.fifthnine.yml` and the support matrix (a billion-laughs file exits 2 in well under a second); Kubernetes manifests are read with the libyaml C composer, which builds nodes without expanding aliases, capped at 200 documents per file. Deeply nested YAML or TOML is reported as a parse error for that file and the scan continues. Parse error messages have quoted values replaced with `****`, so a malformed secret is not echoed into the report. There is no per-file parse timeout and no per-scan time budget in v0.1; the 1 MiB file cap, the YAML prefilter and the C composer bound the work instead.

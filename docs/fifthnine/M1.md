## Discovery rules

Walk order is sorted by name. Never followed: symlinks (inside the repo: skipped as `ignored`; pointing outside: `symlink_outside_root`). Built-in excluded directories: `.git .hg .svn node_modules .venv venv __pycache__ .tox .nox .mypy_cache .pytest_cache .ruff_cache .gradle .idea .vscode target build dist .terraform vendor site-packages .eggs`, plus any directory containing `pyvenv.cfg` (a virtualenv under any name). Names such as `env` are deliberately not excluded because teams keep per-environment manifests there. Consequence: anything a team keeps under those names (for example Kubernetes YAML in a `build/` directory) is not inventoried; the coverage section lists the excluded directories. The root `.gitignore` and `.fifthnine.yml` `ignore_paths` apply with gitignore semantics; nested `.gitignore` files are not read in v0.1. Files FifthNine parses are capped at 1 MiB (`--max-file-size`) and checked for NUL bytes; other files are only counted. The walk stops at 20,000 files with a blocking coverage notice.

## Detection rules and limits

Values come from parsers. Line numbers come from the XML and YAML parsers, and from an exact-text search for the parsed value in TOML and requirements files. When the same component version is found in several files, one entry is kept: lockfile first, then build descriptor, then Dockerfile. Different versions of the same component are all kept.

- Maven: `${property}` resolved one level from the same POM only. Parent POM inheritance, profiles and `${revision}` from CI flags are not resolved; the version is reported as not determined.
- Gradle: literals only. Version catalogs (`libs.versions.toml`) are read. Values computed in Groovy or Kotlin DSL, `buildSrc` and settings plugin management are reported as not determined.
- Python: exact pins (`==`) and lockfiles only. A range such as `fastapi>=0.110` without a lockfile gives "version not determined", never a guessed version. `requires-python` is not treated as the runtime version.
- Spring Framework is reported only when declared explicitly; the Boot-managed version is not inferred in M1.
- Kubernetes: every object's `apiVersion`/`kind` is inventoried. Kinds v0.1 reads are listed in the stack; other workload kinds (StatefulSet, DaemonSet, Job, CronJob, Pod, ReplicaSet, Argo Rollout) are listed as unsupported; non-workload kinds appear only in facts.
- Helm templates are detected by template syntax and skipped; Kustomize overlays are detected and not built (E3).
- Java, Kotlin and Python source files are counted, not parsed. Spring configuration files are inventoried; profile resolution starts in M2.

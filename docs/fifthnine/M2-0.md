## Development corpus

### Selection criteria

A repository is eligible when all of these hold:

- **C1. Licence.** It is public and every part used for measurement carries an OSI-approved licence. Repositories with no licence file, a non-OSI licence (including CC0), or a commercially licensed part are excluded.
- **C2. Application source.** It contains the source of at least one Spring Boot or FastAPI application.
- **C3. Deployment config in the repository.** Its Kubernetes deployment configuration deploys an image of that in-repository application. The configuration may be plain manifests, Kustomize or Helm. At most two Helm-only repositories per framework are included.
- **C4. It is one application, not a collection.** Libraries, framework repositories, sample collections, and repositories that repeat an application per section or chapter are excluded, because they would count one application many times. A single-application sample, tutorial, book or course repository is admitted only into the educational cohort (below).
- **C5. Size.** Under the 20,000-file limit.
- **C6. Mix.**
  - Ten repositories per framework.
  - At least four Spring Boot repositories inside the approved 3.2 to 3.5 range at the pinned commit.
  - At most two repositories per owner.
  - Out-of-range slots go to repositories that add a case the others do not cover.
- **C7. Pinned commit.** The commit is the default-branch HEAD on the selection date (2026-10-21 to 2026-10-22). No older commit was chosen to make a repository fit.
- **C8. No selection on FifthNine output.** The M1 scanner ran over the candidates only to read detected framework versions for C6.

### Cohorts (CEO decision D1)

Each entry has a `cohort`:
- **generalization:** a maintained open-source application or platform released for production use by others. Only this cohort supports claims about how M2 extraction generalizes to real repositories.
- **educational:** a sample, demo, tutorial, training project, vendor reference application, or book or course companion code. These entries are fixtures for known patterns and traps. Their results are reported separately and never pooled into generalization figures.

The first version of the corpus was not classified this way. Applying the definition to all 20 original entries, not only the two the CEO named (PolarBookshop/catalog-service, a book companion, and DevOps-Boot/fastapi-k8s, a training project), puts all 10 Spring entries and 4 FastAPI entries in the educational cohort. Without additions, the corpus would have measured no real-world Spring extraction at all.

I therefore probed a further 20 maintained Spring Boot applications, chosen before running FifthNine on them. I applied C1 to C6 unchanged and admitted every candidate that qualified, with one exception required by the owner cap: apache/dolphinscheduler, the third Apache project, was left out because it is Helm-only and C3 already ranks Helm-only below plain manifests. This added SB-11 to SB-16. FifthNine output was read only for the C6 version check, as for the original entries (C8).

### Linkage expectation

Each entry's `linkage_expectation` applies one rule, derived from the proposal evidence in ARCHITECTURE.md "Service linkage" and checked by script against each clone:
- **in-repo-app:** a deployed workload's image basename matches an in-repository build identity (Maven `artifactId`, `pyproject` name), and exactly one in-repository Dockerfile builds that application.
- **partial:** an image plausibly corresponds to in-repository source, but that evidence cannot confirm it. Typical causes: the image is built without a Dockerfile (buildpacks, Maven or Gradle image plugins), there is no build identity (requirements.txt only), there are several Dockerfiles, names are prefixed, or image references are placeholders.
- **none:** no deployed workload image corresponds to in-repository source, or deployment is Helm-only.

Result on the original 20 entries: 2 in-repo-app (SB-02, SB-10), 14 partial, 4 none. This measurement is preserved as recorded, and the evidence requirements are unchanged (CEO decision D1). On the 6 added entries the same rule gives 2 in-repo-app (SB-11, SB-14), 3 partial and 1 none. By cohort, 2 of 12 generalization entries and 2 of 14 educational entries satisfy the rule. This is the most important finding of M2-0 for M2-5. The M0 linkage rules propose a link for very few real repositories, because buildpack-built images and requirements-only Python projects are common. M2-5 has to measure this on the corpus, per cohort. Any proposal to change the evidence rules must come with false-link measurements; a change is not justified by coverage alone.

## Fact answer keys

### What is labelled

Each sample has one key in `default` mode: `fifthnine scan .` with no `.fifthnine.yml`, so the container-to-source link is inferred. Facts are tagged with the M2 PR that must produce them.

| Sample | Facts | M2-1 | M2-2 | M2-3 | M2-4 | Defaults cited | Negative keys |
|---|---|---|---|---|---|---|---|
| orders-service-spring | 74 | 32 | 32 | 0 | 10 | 14 | 4 |
| catalog-api-fastapi | 56 | 26 | 0 | 30 | 0 | 4 | 5 |

Each labelled fact gives:
- `kind`, `subject` and `scope`;
- the expected `value`, `unit` and `status`, plus `absent` when a field is established as not set;
- `override_exposure`, with structured `exposure_sources`: the out-of-repository object, how it attaches, and example variables, or the facts whose exposure it inherits;
- the `source` location;
- every contributing location or fact in `inputs`, each with a role;
- the `precedence` level that won, the facts it `supersedes`, and the `link_ids` it depends on;
- for `default` facts, `default_ref` with repository, tag, commit, file, line and anchor.

Negative keys use a closed predicate vocabulary: kind, subject, scope, source path, value, value contains, value is null, input fact with input role, and status. `value_contains` is a substring match on a string, or on any element of a list. The model evaluates every negative key against the key's own facts and fails if any of them matches. They encode the M0 traps: a prod fact taken from `application-dev.yml` (F3), `--reload` in the effective command (F13), `requires-python` read as the runtime version, an invented `/readyz` route, and any resolved value from an out-of-repository Secret.

### Status conventions

These follow `derive_verdict()` in `schema/v1.py`, so that labelled statuses produce the verdicts RULES.md documents:

- **declared:** a literal in an active source, or a value derived only from declared facts and cited defaults. Derived values are not marked inferred: in v1, `inferred` always adds a `linkage_inferred` assumption, which would stop rules such as FN-DEP-003 S3 and FN-DEP-002 R2 from ever reaching VIOLATION.
- **declared with `absent: true`:** a field established as not set in the cited object. An example is the missing CPU request, which FN-CAP-002a H1 expects to give VIOLATION. Admission-time injection is a rule-side `cluster_admission_default` assumption (H6), not an unknown value.
- **default:** a framework default for a resolved component version, with an upstream citation and a `version_basis` input whose value and component match `applied_version` and the framework. Kubernetes defaults follow decision D3 (below).
  - A default that fills an unset field always has an `absence` input: the line of the nearest enclosing object or section that exists in the source, or the construction site for code (`new RestTemplate()`). Managed versions (`stack.version`) are exempt because they fill no field.
  - A default whose value is null (SP-J06, a null `Duration`) means the framework's default is "no value", here no read timeout. That is different from `absent`, which says the repository does not set a field.
- **unresolved:** the repository has no value. The value is null and a reason is given. One fact uses it: CA-K02, the unset namespace.
- **inferred:** reserved for genuine heuristics. The keys use none.
- **Derived facts inherit.** A fact derived from an exposed value is itself exposed, a fact derived from link-dependent values carries those links, and a declared fact cannot be derived from an unresolved one. The model enforces all three for `value_source` inputs.
- **References to out-of-repository objects:** an `envFrom` reference to a Secret is a declared reference. The Secret's unknown contents show up only as `env_possible` on the facts it could replace.

### How the keys encode the CEO's three requirements

**Repository-resolved versus production-effective (M2-R1).** No key states a production-effective value. A value is repository-resolved, and three fields show what could still change it: `override_exposure` with its named source, the `link_ids` it depends on, and `unresolved` where the repository has no value.

For example, `clients.payment.base-url` resolves to `http://payments.commerce.svc.cluster.local` from the in-repository ConfigMap. The key records:
- the placeholder and the `envFrom` attachment as inputs;
- that the Secret is attached later and wins duplicates, and the variables that could carry an override;
- the dependency on link SP-L01.

A test enforces that every Spring property and pydantic-settings fact names its link.

**Provenance for derived values (M2-R2).** A derived value lists every input. The readiness endpoint `8081:/actuator/health/readiness` lists every input of the RULES.md FN-DEP-002 path algorithm, ten in all:
- `server.port` and `management.server.port`;
- the `/actuator` and empty management base-path defaults;
- the health path mapping (none, so `health`);
- probe-group activation on Kubernetes and the `add-additional-paths` default;
- the exposure include list, the empty exclude list, and the 3.4 health endpoint access (unrestricted).

Default inputs are cited at Boot 3.4.13.

**Framework-version semantics.** Eighteen `default` facts cite an upstream file and line at a pinned tag and commit:
- Spring Boot 3.4.13: shutdown mode, actuator base paths, path mapping, exposure exclude, health access, probe-group activation, additional paths, and the managed Spring Framework version;
- Spring Framework 6.2.15: RestTemplate timeouts, RestClient factory selection, and the JDK client read timeout;
- FastAPI 0.159.1: `debug`;
- tenacity 9.2.1: `stop_never`;
- Kubernetes: grace period, strategy type, and `maxUnavailable`.

Notes record where the answer changes by version. For example, `server.shutdown` is `immediate` on Boot 3.2 and 3.3, and `spring.http.client.*` binds to nothing before 3.4.

### Scoring, from M2-1 on

An extractor fact matches a key fact on `(kind, subject, scope)`. A matched key fact is **correct** only when all of these match:
- value, unit, status and `absent`;
- `override_exposure`, and the set of `exposure_sources` objects and attachments (variables are illustrative and not scored);
- source path and line;
- the set of inputs, compared as (role, path:line) or (role, matched fact);
- `precedence` (closed vocabulary in `answer_keys.PRECEDENCE`), `link_ids` and `overridden_by`;
- for defaults, framework, applied version, tag, path and line.

Otherwise it is classified by the first field that differs. A key fact with no match is **missing**. An extractor fact with no key entry is **unlabelled** and is listed for review, because keys do not try to list every fact a repository contains. A violated negative key fails the run.

The gate for each PR (M2_PLAN.md criterion 3): every key fact tagged with that PR's milestone or an earlier one is correct, and no negative key is violated. The model rejects any key fact that depends on a fact or link from a later milestone.

### Kubernetes defaults (CEO decision D3)

The cluster version and its admission configuration are never in the repository. A Kubernetes default may therefore be used only when its behaviour is verified across the supported Kubernetes versions:

- **Supported versions:** the releases maintained upstream on the selection date (1.35, 1.36, 1.37), plus 1.34, which reaches end of life on 2026-10-27, so that recently supported clusters are covered.
- **What was verified:** each cited default line was read at the latest patch of every one of those releases (v1.34.12, v1.35.9, v1.36.5, v1.37.1) and found identical:
  - `DefaultTerminationGracePeriodSeconds = 30`;
  - RollingUpdate as the default strategy;
  - 25% `maxUnavailable` and `maxSurge`.
- **How it is cited:** at v1.37.1, commit f78e722, with `verified_at` listing all four releases and `applied_version` null. The model rejects a version-independent default without at least two verified releases, including the cited one.
- **What stays limited:** a mutating admission webhook can still change these values. Notes on every Kubernetes default say it is the documented default, never an observed production value. Admission effects stay rule-side assumptions (`cluster_admission_default`).

M2-1 records the supported range in the packaged support matrix, which today lists Kubernetes API groups but no server versions.

## Provenance schema assessment (requirement M2-R2)

Labelling showed where `fifthnine.result/v1` revision 2 falls short for derived values and known absence:

| Gap | Example | Effect without a change |
|---|---|---|
| A fact can cite only one location | `clients.payment.base-url`: placeholder, ConfigMap entry, `envFrom` attachment | Two of the three inputs disappear |
| Nothing names the source behind `env_possible` | Secret `orders-service-secrets`, applied after the ConfigMap | The reader sees "may be overridden" but not by what |
| A fact cannot say which linkage it depends on | Spring properties apply only through the inferred link | `--facts all` cannot show that a value is conditional on an unconfirmed link |
| No precedence level is recorded | `application-prod.yml` over `application.yml`; gunicorn CLI over the config file | The reader cannot see why one value won |
| No way to say "established as not set" | No CPU request; no preStop hook | Absence must be labelled unresolved, so `derive_verdict` returns UNKNOWN where RULES.md expects VIOLATION or CONDITIONAL |
| `DefaultRef` has no exact version, commit or line | Boot 3.4.13 `server.shutdown`, `ServerProperties.java:117` | Citations cannot be checked mechanically |

### Proposed change: revision 3

| Model | New field | Type, default |
|---|---|---|
| `Fact` | `inputs` | list of `FactInput {role, source: SourceRef or null, fact_id: str or null}`, defaulting to empty |
| `Fact` | `exposure_sources` | list of `ExposureSource {via, object, variables, from_fact_ids}`, defaulting to empty |
| `Fact` | `link_ids` | list of strings, defaulting to empty (more than one link is possible) |
| `Fact` | `precedence` | string or null, from a documented vocabulary such as `spring.packaged_profile_file:prod`, `spring.os_environment`, `k8s.container.command`, `gunicorn.cli`, `docker.entrypoint` |
| `Fact` | `absent` | bool, defaulting to false |
| `DefaultRef` | `applied_version` | string or null |
| `DefaultRef` | `upstream` | `{repository, tag, commit, path, line, anchor, verified_at}` or null. `verified_at` lists the releases where the default was checked identical (D3) |

`derive_verdict()` treats an `absent` declared fact as established. No other verdict logic changes. When `applied_version` is null, the existing required `version_range` states the verified span (for Kubernetes, `>=1.34,<=1.37`), and `upstream.verified_at` must list at least two releases including the cited one; output without that cannot claim a version-independent default.

**Compatibility, stated correctly this time.** SCHEMAS.md allows additive optional fields within v1, so the identifier stays `fifthnine.result/v1`. However, the published `schemas/result.v1.json` sets `additionalProperties: false` on `Fact` and `DefaultRef`, and the v1 models use `extra="forbid"`. A consumer that validates revision 3 output against the revision 2 JSON Schema will therefore reject it. No external consumer exists yet (nothing is released), so the practical cost today is zero. The schema files and models are regenerated together, and SCHEMAS.md records the revision.

The alternative is to call this `fifthnine.result/v2`. That is cleaner for future consumers but breaks the R2 decision to keep v1. I recommend revision 3 within v1 before the alpha, with a rule that after the alpha any field addition ships with a relaxed or versioned JSON Schema.

Not proposed:
- **A `supersedes` field.** It is derivable from `overridden_by`.
- **A production-effective flag.** FifthNine never asserts one.

**Approved (CEO decision D2).** Revision 3 is implemented in M2-1 within `fifthnine.result/v1`, with regenerated schemas, validator tests and a SCHEMAS.md entry that documents the strict-consumer incompatibility. Breaking changes after the public alpha require explicit versioning.

## Network-enabled fixtures (requirement M2-R3)

M2-0 adds no network job. The plan for the D3 job, implemented in M2-2:

## Development corpus

### Selection criteria

A repository is eligible when all of these hold:

- **C1. Licence.** It is public and its licence file carries an OSI-approved licence. Repositories with no licence file or a non-OSI licence are excluded, because the keys will quote file paths and short excerpts.
- **C2. Application source.** It contains the source of at least one Spring Boot or FastAPI application.
- **C3. Deployment config in the repository.** It contains Kubernetes deployment configuration: plain manifests with at least one Deployment or StatefulSet, Kustomize, or Helm charts. At most two Helm-only repositories per framework are included, to measure the E3 gap without dominating the corpus.
- **C4. It is an application, not a collection.** Libraries, framework repositories and sample collections are excluded: spring-cloud-kubernetes, dapr/quickstarts, kubernetes-engine-samples, and a book repository that repeats one application per chapter.
- **C5. Size.** Under the 20,000-file limit.
- **C6. Mix.**
  - Ten repositories per framework.
  - At least four Spring Boot repositories inside the approved 3.2 to 3.5 range at the pinned commit.
  - At most two repositories per owner.
  - Out-of-range slots go to repositories that add a case the others do not cover, such as probe focus, image placeholders, Config Server, many services with a Dockerfile each, or near the file limit.
- **C7. Pinned commit.** The commit is the default-branch HEAD on the selection date (2026-10-21 to 2026-10-22). No older commit was chosen to make a repository fit.
- **C8. Selection never depends on FifthNine output.** The M1 scanner ran over the candidates for one purpose only: reading detected Boot versions to apply C6. It was not used to prefer repositories on which FifthNine performs well.

### Process

GitHub search is not available from this environment, so candidates came from web searches and from projects known to deploy Spring Boot or FastAPI on Kubernetes. 79 candidates were listed and 77 cloned; two names did not exist. Each was checked by script for:
- the licence file;
- Spring Boot or FastAPI build references;
- FastAPI imports;
- plain `kind: Deployment|StatefulSet` manifests outside Helm `templates/`;
- `Chart.yaml` and `kustomization.yaml`;
- the file count.

Every rationale in `corpus.v1.yaml` was then checked against the clone. Four claims were wrong or could not be verified, and I corrected them before submission. One example: feast's manifests deploy a published image that no in-repository Dockerfile builds, so its linkage expectation is `none`, not `partial`.

### What the baseline already shows

These are measurements from M1 at `d58bcbe`, not M2 results.

- **Boot version not detected in two Gradle repositories.** SB-09 and SB-10 set the version through Gradle properties or buildscript variables, which M1 does not read. M2-2 must report these as version not determined with a reason; the corpus will count how often that happens.
- **Nothing detected in FA-06.** Its dependencies live in `requirements/*.txt`, a directory layout M1 does not match. I will fix this in M2-3 and record it there.
- **FastAPI versions are rarely pinned.** Six of ten FastAPI repositories have no determinable FastAPI version, so version-dependent defaults will mostly be unresolved. That is the intended behaviour, and it limits how much framework semantics can apply to Python repositories.
- **Placeholder images.** SB-03 and SB-04 use images such as `<acr-name>.azurecr.io/gateway:<tag>`, so linkage cannot be inferred from image names there.
- **Scan times** were between 0.27 s and 2.4 s per repository, with the largest at 14,335 files considered.

## Fact answer keys

### What is labelled

Each sample has one key in `default` mode: `fifthnine scan .` with no `.fifthnine.yml`, so the container-to-source link is inferred. Facts are tagged with the M2 PR that must produce them.

| Sample | M2-1 | M2-2 | M2-3 | M2-4 | M2-5 | Negative keys |
|---|---|---|---|---|---|---|
| orders-service-spring | 29 | 26 | 0 | 9 | 1 | 5 |
| catalog-api-fastapi | 22 | 0 | 25 | 0 | 1 | 5 |

Each labelled fact gives:
- `kind`, `subject` and `scope`;
- the expected `value`, `unit` and `status`;
- `override_exposure`, plus the named mechanism in `exposure_sources`;
- the `source` location;
- every contributing location in `inputs`, each with a role: placeholder, env definition, env attachment, profile activation, reference, absence, version basis;
- the `precedence` level that won and the facts it `supersedes`;
- the `link` the value depends on;
- for `default` facts, the upstream citation: repository, tag, commit, file, line and anchor text.

Negative keys name things the extractor must not produce. They encode the M0 traps: a prod fact taken from `application-dev.yml` (F3), `--reload` in the effective command (F13), `requires-python` read as the runtime version, an invented `/readyz` route, and any value taken from an out-of-repository Secret.

### How the keys encode the CEO's three requirements

**Repository-resolved versus production-effective.** No key states a production-effective value. Each value is the repository-resolved one, and three fields show what could change it:
- `status`: `unresolved` when the repository has no value;
- `override_exposure` with `exposure_sources`: names the out-of-repository Secret and the variables it could set;
- `link`: the inferred container-to-source link the value depends on.

For example, `clients.payment.base-url` resolves to `http://payments.commerce.svc.cluster.local` from the in-repository ConfigMap. The key records three things:
- the placeholder at `application.yml:27` and the `envFrom` entry as inputs;
- that the out-of-repository Secret is attached after the ConfigMap and would win if it defines `PAYMENT_BASE_URL`;
- that the value depends on link SP-L01.

A test enforces that every Spring property and pydantic-settings fact names its link.

**Provenance for derived values.** A derived value lists all its inputs. The readiness endpoint `8081:/actuator/health/readiness` lists three inputs: `server.port`, `management.server.port`, and the `/actuator` base-path default with its Boot 3.4.13 citation. The effective container command shows that the Deployment set no `command` and the Dockerfile `ENTRYPOINT` won.

**Framework-version semantics.** Eight `default` facts cite an upstream file and line at a pinned tag and commit:
- Spring Boot 3.4.13: `server.shutdown`, the actuator base path, and the managed Spring Framework version;
- Spring Framework 6.2.15: the RestTemplate timeouts;
- FastAPI 0.159.1: `debug`;
- tenacity 9.2.1: `stop_never`;
- Kubernetes: the grace-period default.

Each default names the version fact it was looked up for. The notes record where the answer changes by version: `server.shutdown` is `immediate` on Boot 3.2 and 3.3, and `spring.http.client.read-timeout` binds to nothing before 3.4.

### Scoring, from M2-1 on

An extractor fact matches a key fact on `(kind, subject, scope)`. Each key fact then scores as one of:
- **correct:** value, status, override exposure and source all match;
- **wrong value**;
- **wrong status:** includes a value reported as resolved when the key says unresolved;
- **wrong location;**
- **missing.**

An extractor fact with no key entry is listed as **unlabelled** for review, not counted as wrong, because the keys do not try to list every fact a repository contains. A negative key that is violated fails the run.

The gate for each PR (M2_PLAN.md criterion 3): every key fact tagged with that PR's milestone or an earlier one scores correct, and no negative key is violated.

### Corpus keys

The samples were labelled by me, and I am also writing the extractors. That is a conflict, so the corpus keys will be labelled independently:
- For each M2 PR, an agent that has not seen the extractor code labels the same fact kinds on a fixed subset of corpus repositories (two per framework, chosen by corpus id before labelling starts), using the same format.
- Disagreements between the labeller and the extractor are adjudicated one by one, and each decision is recorded in the PR.
- The provenance oracle (M2_PLAN.md criterion 2) runs on all 20 repositories without keys, because it checks the extractor's own claims against the files.

### Limits of the keys

- One person labelled the sample keys. Before M2-1 merges, the independent M2-0 reviewer checks them against the sources (see acceptance evidence below).
- Upstream citations are checked by the validator for format only. The cited lines were read from tagged source fetched for this PR. The Spring runtime-fixture job (D3) will re-verify the Spring ones in M2-2.
- Keys cover the first-wave rule inputs, not every fact.

## Provenance schema assessment (requirement 2)

Labelling the keys showed where `fifthnine.result/v1` revision 2 falls short. A `Fact` already carries `status`, `override_exposure`, `scope`, one `source`, `default_ref` (framework, version range, title and URL), `overridden_by` and `unresolved_reason`. That is enough for literal values, but not for derived ones:

| Gap found while labelling | Example | Effect without a change |
|---|---|---|
| A fact can cite only one location | `clients.payment.base-url` comes from a placeholder, a ConfigMap entry and an `envFrom` attachment | Two of the three inputs disappear from the report |
| Nothing names the out-of-repository source behind `env_possible` | The Secret `orders-service-secrets` and the variables it could set | The reader sees "may be overridden" but not by what |
| A fact cannot say which linkage it depends on | Every Spring property applies to the container only through the inferred link | `--facts all` cannot show that a value is conditional on an unconfirmed link |
| No precedence level is recorded | `application-prod.yml` beat `application.yml`; gunicorn CLI beat the config file | The reader cannot see why one value won |
| `DefaultRef` has no exact version, commit or line | The Boot 3.4.13 default for `server.shutdown`, `ServerProperties.java:117` | The citation cannot be checked mechanically or tied to the version it was looked up for |

### Proposed change: revision 3, additive only

| Model | New optional field | Type |
|---|---|---|
| `Fact` | `inputs` | list of `FactInput {role, source: SourceRef or null, fact_id: str or null}`, defaulting to empty |
| `Fact` | `exposure_sources` | list of strings, defaulting to empty |
| `Fact` | `link_id` | string or null |
| `Fact` | `precedence` | string or null, from a documented vocabulary such as `spring.packaged_profile_file:prod`, `spring.os_environment`, `k8s.container.command`, `gunicorn.cli`, `docker.entrypoint` |
| `DefaultRef` | `applied_version` | string or null |
| `DefaultRef` | `upstream` | `{repository, tag, commit, path, line}` or null |

Under the SCHEMAS.md versioning policy, additive optional fields are allowed within v1. The schema id stays `fifthnine.result/v1`, existing consumers keep working, and M1 output is unchanged because empty lists and nulls are the defaults.

Not proposed:
- **A `supersedes` field.** It is derivable from `overridden_by`; the keys use it only as a cross-check.
- **A "production-effective" flag.** FifthNine never asserts one. The fields above, together with linkage status, are how a reader tells whether anything could still change a value.

This is a proposal. Nothing is implemented. If approved, M2-1 implements it with schema export, JSON Schema regeneration, a SCHEMAS.md entry, and validator tests (for example: `inputs` entries name exactly one target, and `default` facts carry `applied_version` or a note).

## Network-enabled fixtures (requirement 3)

M2-0 adds no network job. The plan for the D3 job, implemented in M2-2:
- It lives in a separate workflow file, triggered only by changes under `fixtures/runtime/` or by manual dispatch.
- It has no repository secrets and gets read-only `contents` permission.
- It never installs or imports the scanner's runtime path.

It produces observations: the actual default values and the actual actuator paths per Boot version. These are committed as data and reviewed. The offline test suite reads that data and never runs the job. `fetch.py` follows the same separation: it is benchmark tooling, and no offline test calls it.

## Clarifications to the M2 plan found while labelling

1. **Tenacity facts.** M2-3 also extracts tenacity decorator arguments (CA-T01 to CA-T04), because FN-RES-004 is a first-wave rule. The plan's Python item listed only configuration.
2. **No Python HTTP timeout facts.** That check is delegated to Ruff S113 and Bandit B113 (M0-D4). A negative key enforces it.
3. **Unset Kubernetes namespace.** Subject keys use `_` when an object has no `metadata.namespace`, and the namespace fact is unresolved (CA-K02).

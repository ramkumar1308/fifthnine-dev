# M2-1: Docker and Kubernetes facts, workload graph, override exposure, linkage proposals

Status: READY FOR REVIEW after the independent review below. Not merged. Branch `feature/m2-1-deployment-facts`. Plan: `M2-1_PLAN.md`. Scans still report `INCOMPLETE`, there are no rules, and nothing reaches the network.

## What was delivered

- **Schema revision 3, within v1 (M2-0-D2).** Additive fields on `Fact` (`inputs`, `exposure_sources`, `link_ids`, `precedence`, `absent`) and on `DefaultRef` (`applied_version`, `upstream`). Revision 2 documents stay valid. The rule that a fact with exposure other than `none` names its sources is enforced on engine output in a test, not in the model, so that revision 2 documents still load.
- **Dockerfile parser** (`extract/dockerfile.py`): continuations, `escape`, stages, `ARG` and `ENV` substitution, `WORKDIR`, `EXPOSE`, `ENTRYPOINT` and `CMD` (including BuildKit's clearing of an inherited `CMD`), `COPY --from`, `USER`. Heredocs and `ONBUILD` are reported as unsupported. No execution.
- **Kubernetes facts** (`extract/k8s.py`, `resolve/deployment.py`): Deployment, Service, Ingress, HPA, PDB and ConfigMap, with selectors, namespaces, ports, probes, `preStop`, resources, environment and volume mounts. Items inside `kind: List`, StatefulSet, DaemonSet, Job and CronJob stay out of scope and are listed in coverage.
- **Kubernetes defaults** (`data/defaults/kubernetes.v1.yaml`): eight entries, each cited at v1.37.1 (commit f78e722) and verified identical at v1.34.12, v1.35.9, v1.36.5 and v1.37.1. A default is accepted only with two or more verified releases.
- **Environment model:** explicit `env` beats `envFrom`, later `envFrom` sources win, out-of-repository sources are named as exposure sources, and a mount at the image `WORKDIR` marks the container `file_possible` (X1 to X5).
- **Effective command** with Kubernetes semantics (F13, F14). A `$(VAR)` in the command or args leaves it unresolved.
- **Linkage proposals** under the ARCHITECTURE.md evidence rule, unchanged (M2-1-D1).
- **Support matrix:** new `kubernetes-server` entry for 1.34 to 1.37. No version is marked tested.

## CEO clarifications

**Default stage versus deployed image.** Two facts are kept apart. `docker.default_target` is declared: the final stage, which Docker builds when no `--target` is given. `docker.build_target` is unresolved, because the production target is not in the repository. Every proposed link carries the evidence note "assumes the deployed image was built from the Dockerfile's default (final) stage; the build target used in production is not in the repository", and the effective-command fact that depends on a link stays `inferred`.

**Provenance validated against source semantics.** The test oracle (`tests/support/oracle.py`) does not look for field names. It re-reads Kubernetes with ruamel's round-trip loader and Dockerfiles with the `dockerfile` package (Docker's BuildKit parser, MIT, a dev-only dependency pinned to 3.4.0), then recomputes independently: values, lines, selector and namespace relationships, port resolution, defaults, exposure, the BuildKit `ENTRYPOINT` and `CMD` rule, effective commands, and the lines cited as link evidence (the line must be a `FROM`, `COPY`, `ADD` or `EXPOSE` instruction, an `<artifactId>`, a `rootProject.name` assignment, the project name in `pyproject.toml`, or the image value). Mutation tests alter a value, a line and a relationship and require the scorer and oracle to fail.

## Linkage

Expectation labels come from M2-0. The comparison is: `in-repo-app` means at least one proposed link; `partial` and `none` mean no proposed link.

Two disagreements with the M2-0 labels, both explained, neither resolved by changing the rule:

- **SB-14 (seata), label corrected to `partial`.** The Dockerfile sits in `distribution/docker/server`, not in the `seata-server` module root, and copies `ADD target` and similar directories from a build context the repository does not connect to `server/pom.xml`. The evidence rule is not met, so the engine reports the link unresolved. The M2-0 label judged the layout by reading it, not by applying the rule. The correction and its reason are recorded in `corpus.v1.yaml`.
- **SB-10 (ftgo), label kept, disagreement stands.** The services have Dockerfiles next to the source, but the manifests use `extensions/v1beta1` and `apps/v1beta1`, which are outside the supported API set. They are not read, and coverage says so. The M2-0 label measured layout and ignored the API version. The result is correct for the supported range and is not tuned.

### False-linkage audit

All 24 proposed links were checked by hand against the cited source lines.

- **12 links hold on strong evidence:** 4 in bank-of-anthos (Dockerfile in the module root, image basename equal to the `pyproject` name) and 8 in shenyu examples and integrated tests (`ENV APP_NAME` equal to the module's `artifactId`, then `ADD target/${APP_NAME}.jar`, with a matching `EXPOSE`).
- **12 links hold, but the build evidence is weak (shenyu-admin 6, shenyu-bootstrap 6).** The Dockerfile is in `shenyu-dist/.../docker`, and the COPY that satisfies the rule is `COPY --from=prepare /opt/shenyu-admin ...`. The artifact name matches a directory chosen inside the image, not a built artifact; the real artifact is `ADD target/${APP_NAME}.tar.gz`, whose name is a build argument (`ARG APP_NAME`) with no default. The links are probably right (the distribution module packages that application), but the stated rule is satisfied by a path segment that is not an artifact. No link was found to be wrong. This is a rule-quality finding, not a defect of the implementation, and the rule is unchanged. A proposal to require that a `--from` source be an artifact file (`.jar`, `.war`, `.tar.gz`, wheel) would turn these 12 links into unresolved ones; it needs CEO approval and a false-link measurement on a held-out set, per M2-0.
- Unresolved links name the missing evidence: no Dockerfile builds the module (buildpacks or plugins), no matching build identity (third-party images such as `postgres` and `redis`), an ambiguous identity or Dockerfile, container ports that the Dockerfile does not expose, or a placeholder image reference.

## Known limitations

- The Docker build target, CI build arguments and the cluster version are not in the repository. Nothing here treats the default stage as the deployed image.
- Helm and Kustomize are not rendered (E3). Admission webhooks and LimitRanges can change values after apply.
- Images built without a Dockerfile (buildpacks, Jib, image plugins) cannot be linked under the evidence rule.
- A link rests on one Dockerfile and one default stage; see the weak-evidence finding above.
- Application facts that depend on the container environment arrive in M2-2 and M2-3.
- The `dockerfile` wheel (Go parser) must install on every CI platform. This is confirmed only when CI runs.

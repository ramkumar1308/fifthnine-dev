# M2-1: Docker and Kubernetes facts, workload graph, override exposure, linkage proposals

Status: READY FOR REVIEW once CI is green on all seven jobs. Not merged. Branch `feature/m2-1-deployment-facts`. Plan: `M2-1_PLAN.md`. Scans still report `INCOMPLETE`, there are no rules, and nothing reaches the network.

## What was delivered

- **Schema revision 3, within v1 (M2-0-D2).** Additive fields on `Fact` (`inputs`, `exposure_sources`, `link_ids`, `precedence`, `absent`) and on `DefaultRef` (`applied_version`, `upstream`). Revision 2 documents stay valid. The rule that a fact with exposure other than `none` names its sources is enforced on engine output in a test, not in the model, so that revision 2 documents still load.
- **Dockerfile parser** (`extract/dockerfile.py`): continuations, `escape`, stages, `ARG` and `ENV` substitution, `WORKDIR`, `EXPOSE`, `ENTRYPOINT` and `CMD` (including BuildKit's clearing of an inherited `CMD`), `COPY --from`, `USER`. Heredocs and `ONBUILD` are reported as unsupported. No execution.
- **Kubernetes facts** (`extract/k8s.py`, `resolve/deployment.py`): Deployment, Service, Ingress, HPA, PDB and ConfigMap, with selectors, namespaces, ports, probes, `preStop`, resources, environment and volume mounts. Items inside `kind: List`, StatefulSet, DaemonSet, Job and CronJob stay out of scope and are listed in coverage.
- **Kubernetes defaults** (`data/defaults/kubernetes.v1.yaml`): eight entries, each cited at v1.37.1 (commit f78e722) and verified identical at v1.34.12, v1.35.9, v1.36.5 and v1.37.1. A default is accepted only with two or more verified releases.
- **Environment model:** explicit `env` beats `envFrom`, later `envFrom` sources win, out-of-repository sources are named as exposure sources, and a mount at the image `WORKDIR` marks the container `file_possible` (X1 to X5).
- **Effective command** with Kubernetes semantics (F13, F14). A `$(VAR)` in the command or args leaves it unresolved. When the Dockerfile sets no ENTRYPOINT and the container sets no `command`, the base image's ENTRYPOINT is unknown, so the fact is unresolved (the image CMD stays reachable through its inputs). An empty `command: []` or `args: []` counts as unset.
- **Linkage proposals** under the ARCHITECTURE.md evidence rule, unchanged (M2-1-D1).
- **Support matrix:** new `kubernetes-server` entry for 1.34 to 1.37. No version is marked tested.

## CEO clarifications

**Default stage versus deployed image.** Two facts are kept apart. `docker.default_target` is declared: the final stage, which Docker builds when no `--target` is given. `docker.build_target` is unresolved, because the production target is not in the repository. Every proposed link carries the evidence note "assumes the deployed image was built from the Dockerfile's default (final) stage", and every fact read through the default stage (effective command, config-location mounts) is `inferred` with a structured reference to the unresolved `docker.build_target` fact. It is never `declared`. The independent review found that an earlier draft marked such facts `declared`; answer key SP-K08 was changed to `inferred` for that reason.

**Provenance validated against source semantics.** The test oracle (`tests/support/oracle.py`) does not look for field names. It re-reads Kubernetes with ruamel's round-trip loader and Dockerfiles with the `dockerfile` package (Docker's BuildKit parser, MIT, a dev-only dependency pinned to 3.4.0), then recomputes independently: values, lines, selector and namespace relationships, port resolution, defaults, exposure, the BuildKit `ENTRYPOINT` and `CMD` rule, effective commands, and the lines cited as link evidence (the line must be a `FROM`, `COPY`, `ADD` or `EXPOSE` instruction, an `<artifactId>`, a `rootProject.name` assignment, the project name in `pyproject.toml`, or the image value). Mutation tests alter a value, a line and a relationship and require the scorer and oracle to fail.

### Evidence rule: what changed after review, and why this is a tightening

The independent reviewer showed that the rule as first implemented accepted links on weaker evidence than ARCHITECTURE.md E4 requires, and the oracle (which only checked that cited lines exist) did not notice. The oracle now re-decides each link (module name on the cited build line, image basename, a COPY or ADD in the default-stage chain that names the artifact or copies module content). It then disagreed with 12 shenyu links, which confirmed the weakness. The implementation was tightened, not loosened:

- A Dockerfile counts as building a module only if a COPY or ADD in its default-stage chain copies the module's artifact, a build-output directory under the module (`target/`, `build/libs/`, `build/`, `dist/`), or the module's application source (`.py`, `.java`, `.kt`), or takes an artifact-suffixed `--from` copy from a stage that copied the module source. A build descriptor alone (`pom.xml`, `requirements.txt`) is not evidence. Sitting in the module directory is not enough. A repository-root module is not copied by an unrelated file such as `nginx.conf`.
- A COPY names the artifact only if the path ends like a build output (`.jar`, `.war`, `.whl`, `.tar.gz`, `.tgz`, `.zip`). A directory that carries the module's name inside an image (`/opt/shenyu-admin`) is not evidence. This turned the 12 shenyu-admin and shenyu-bootstrap links into unresolved ones; before the change they were 12 of 24 proposed links. SB-11 keeps 8 links (the examples and integrated tests).
- If different image repositories would link to one module, none is proposed. Containers that run the same image repository with different tags count as one image.
- An unresolved `EXPOSE` variable is disclosed in the link evidence.

The rule's text is unchanged; the implementation now matches it. The change reduces proposed links from 24 to 12, and no label was changed to follow it. The per-repository agreement with M2-0 labels did not change (25 of 26).

### False-linkage audit

All 12 remaining links were checked by hand against the cited source lines: 4 in bank-of-anthos (Dockerfile in the module root with `COPY . .`, image basename equal to the `pyproject` name) and 8 in shenyu examples and integrated tests (`ENV APP_NAME` equal to the module's `artifactId`, then `ADD target/${APP_NAME}.jar`, with a matching `EXPOSE`). None is wrong. Unresolved links name the missing evidence: no Dockerfile builds the module, no matching build identity (third-party images), an ambiguous identity or Dockerfile, container ports the Dockerfile does not expose, ambiguous images, or a placeholder image reference.

## Known limitations

- The Docker build target, CI build arguments and the cluster version are not read from the repository. Nothing here treats the default stage as the deployed image.
- Helm and Kustomize are not rendered (E3). Admission webhooks and LimitRanges can change values after apply.
- Images built without a Dockerfile (buildpacks, Jib, image plugins) cannot be linked under the evidence rule.
- A link rests on one Dockerfile and one default stage.
- A fact that the base image's ENTRYPOINT would change stays unresolved; the repository cannot show that ENTRYPOINT.
- The open minor items in the review table (10, 13).
- Application facts that depend on the container environment arrive in M2-2 and M2-3.

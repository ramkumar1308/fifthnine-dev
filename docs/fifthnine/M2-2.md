# M2-2: Spring Boot application configuration extraction

Status: AWAITING CEO MERGE APPROVAL after focused validation. Not merged. Branch `feature/m2-2-spring-config`. Plan: `M2_PLAN.md`. Scans still report `INCOMPLETE`, there are no rules, and nothing reaches the network.

## What was delivered

- **Config readers** (`extract/spring_config.py`, `extract/properties.py`): `application.{yml,yaml,properties}` and profile variants, multi-document YAML and `#---` properties documents, YAML 1.1 scalars as SnakeYAML reads them (`off` is a boolean, `0755` is octal), aliases refused, entry and nesting caps, line numbers on every entry.
- **Resolver** (`resolve/spring.py`, `resolve/springprops.py`): production-effective values with Spring Boot's precedence, low to high: config files, OS environment (Dockerfile `ENV` below container `env`), system properties (`JAVA_TOOL_OPTIONS`, `JDK_JAVA_OPTIONS`), `SPRING_APPLICATION_JSON`, command-line `--k=v`. File order follows location, extension and profile rules; profile includes and groups expand as Boot expands them. Placeholders `${name:default}` resolve against the same sources.
- **Overridden facts.** Every shadowed value is emitted with the origin that lost, so a reviewer can see what was set and what won.
- **Exposure.** An `envFrom` Secret or ConfigMap that is not in the repository gives `env_possible` and names the source and the variables that could carry the key. A config directory mounted at the working directory, `SPRING_CONFIG_LOCATION`, `SPRING_CONFIG_ADDITIONAL_LOCATION`, `SPRING_CONFIG_IMPORT`, `spring.config.import` and the `spring-cloud-kubernetes` config dependency give `file_possible`. Derived facts are `inherited` and cite their inputs.
- **Actuator endpoints** derived from the effective properties: management port type (same, different, disabled), base path, path mapping, probe groups, `add-additional-paths`, exposure and access (`access` on Boot 3.4 and later, `enabled` on 3.3 and earlier). The result is a concrete path and port per health endpoint, or an absent endpoint.
- **Defaults table** `data/defaults/spring-boot.v1.yaml` for Boot 3.2 to 3.5. Each default cites the upstream line, and `verified_at` lists the first, middle and latest patch tag of each minor that `verify_upstream.py` re-read.
- **Redaction.** Values of secret-named keys, URL user info and `password=` style query values become `<redacted>` before they reach any fact.
- **Deployment link.** `DeploymentResult` now carries container links and args so the resolver reads the command line and environment of the container that runs the module.

## Runtime comparison (M2-D3)

Workflow `.github/workflows/spring-runtime.yml` is the only job with network access. The CLI stays offline and its contract is unchanged. For each case the harness (`tests/runtime/spring/`) writes a small repository (pom, Dockerfile, Deployment, resources), scans it offline, builds the jar with Maven, and runs it with the same environment, arguments and entrypoint, plus the Kubernetes service variables. A fixture application writes what Spring resolved to JSON: property values, the origin of each (file and line, or the property source), bound defaults, active and default profiles, management port type, health groups. The harness then probes the actuator URLs the scan derived. The result is posted as a pull request comment. The fixture reads nothing from the repository under test.

Boots covered: 3.2.12, 3.3.13, 3.4.13 and 3.5.16 for the defaults table, 3.3.13 and 3.5.16 for the Actuator access cases (`enabled` against `access`); every other case runs on 3.4.13. The 86 cases cover values and types, YAML lists and ISO durations, profile activation from a file, an environment variable and a flag, profile groups and includes, `spring.profiles.default` (including that it is ignored inside a profile file), file order across `classpath:/`, `classpath:/config/`, `.properties`, `.yml` and `.yaml`, every layer of the precedence chain with one layer removed at a time, legacy and uniform environment names, `-D` words before and after `-jar` and the main class, `JAVA_TOOL_OPTIONS` against `JDK_JAVA_OPTIONS`, `SPRING_APPLICATION_JSON` (environment, `-D`, argument), indexed names, repeated options, a bare `--`, `spring.config.location` and `import`, `on-cloud-platform` documents, placeholders (including runtime-supplied names and case), and Actuator paths, ports, probe groups, additional paths, exposure and access.

**What the comparison found.** The first full run reported 0 failures on 63 cases only after three harness defects were fixed (origin wording, absent health bean, system-property origin). It also found one real scanner bug: lists supplied as JSON, `-D` or arguments were dropped. After the second review the case set grew to 86, which produced 69 failures, the JVM being the arbiter of the review's open questions. The scanner was changed until the failures went away, in these ways: profile groups are read from every layer; indexed environment names (`NAME_0_`) form a list; repeated `--k=v` join with commas; `spring.application.json` is read from an argument, a system property or the environment; the main class ends JVM options; a bare `--` ends options; names with uppercase letters or underscores are looked up by their exact spelling in files; an empty top value hides the lower layers; an empty JSON array is an empty value; `on-cloud-platform` documents are evaluated or make their keys unresolved; placeholders for names the JVM or container supplies (`HOSTNAME`, `random.*`, `java.*`) are unresolved. One case (`${random.int:5}`) made Spring itself fail at startup with an `ArrayIndexOutOfBoundsException`; it was replaced by `${random.value:x}`, and startup failures are not an expected outcome in the harness.

**Not compared, counted and not claimed as verified** (final run): default exposure not observed 11, endpoints unresolved 12, probe groups not observable because the health endpoint is absent 7, `spring.active_profiles` unresolved 4, overridden facts 56, unresolved properties 58, and 6 facts whose runtime value differed but which carry a file override exposure flag. Those six come from three cases (`spring.config.import` on the command line, `spring.config.additional-location` as a system property, and an imported file). The scan flags the packaged value as replaceable by a file it did not read, so the difference is the documented exposure. The scanner could read those two classpath files; it does not follow imports. That is a real gap, kept narrow on purpose.

**`spring.profiles.default`.** Spring Boot reads it only when no profile is active, from the layered sources and from the base `application` files, never from a profile-specific file. It names the profiles that are active in that case, `application-default` files are read when nothing is active, and the value is not copied into `spring.profiles.active`. The resolver follows these rules and each of them has a runtime case. The one thing not supported is a default that comes from a source outside the repository, which gives unresolved profiles and unresolved dependent facts.

## Known limits

- Defaults are assumed stable across patch releases inside a minor version. Boot outside 3.2 to 3.5 gets no defaults and unresolved derived facts.
- The contents of a ConfigMap-mounted `application.yml` are not parsed; the mount is reported as exposure only.
- Exposure variables cover the relaxed name, `SPRING_APPLICATION_JSON`, `JAVA_TOOL_OPTIONS` and `JDK_JAVA_OPTIONS`. Other injection routes (init containers, entrypoint scripts) are not modelled.
- `setAdditionalProfiles` in code waits for M2-4. `spring.config.activate.on-cloud-platform` documents are evaluated for a linked container (Kubernetes inferred) and otherwise make their keys unresolved.
- Imported files (`spring.config.import`, `additional-location`) are not read. Values they might replace carry `file_possible`.
- Startup failures (invalid placeholders, bad values, missing required beans) are not predicted. A scan can describe a configuration that Spring refuses to start.
- A second container for one module gets subjects suffixed `@container`; the oracle does not cover those.
- The runtime comparison covers Boot 3.4.13 for the precedence cases; the other minors run the defaults and access cases only. Config tree and file import ordering, environment-variable group binding beyond the tested cases, and keys the scanner never emits are not covered. Defaults are verified at first, middle and latest patch tags per minor, not every patch.

The independent oracle was updated to the same rules from Spring's behaviour, not from the resolver, and each fix has a regression test that runs the oracle. Not checked by the reviewer: the defaults table anchors, `spring.config.import` and `spring.config.location`, `spring.profiles.default`, app-type base paths (`spring.webflux.base-path`, `spring.mvc.servlet.path`), the safe YAML composer, and the tests. Additional known limits from the review: probe groups are not enabled by default on Cloud Foundry (3.4 and later); duplicate YAML keys are not rejected; YAML explicit tags and exponent floats without a dot are typed as strings; `read_only` spellings give an unresolved access; a main class named instead of `-jar` is not detected, so `-D` after it is read as a JVM option; `spring.profiles.default` is not read.

Round 3 found six major and four minor items. Fixed in this PR, each with a unit test (oracle updated to the same rule) and, where the JVM can decide it, a runtime case:

| Finding | Disposition |
|---|---|
| `spring.profiles.include` from several sources kept only the top one; Boot unions them | Fixed: union, highest source first (case `profile-include-union`) |
| A conditional document (`on-cloud-platform`) that sets `spring.profiles.*` was ignored when learning the profiles | Fixed: profiles are unresolved, with the document cited |
| `--key` with no value was ignored; Boot reads it as the empty string | Fixed (case `args-bare-option`) |
| JSON `null` read as an empty string; Boot treats it as absent | Fixed (case `json-null-value`) |
| `${KUBERNETES_SERVICE_HOST:localhost}` resolved to the default | Fixed: the two kubelet variables are runtime-supplied |
| `$VAR` in a shell-wrapped command (`sh -c "java ... --server.port=$PORT"`) read literally | Partly fixed: the word is skipped with a notice, as `$(VAR)` already was. The value it would have set is not marked unresolved |

Open, not fixed, and listed so the CEO can weigh them (all are silent-wrong-value risks in unusual container commands or names, none affect the corpus answer key):

- A shell-form `ENTRYPOINT` with extra Kubernetes `args` or exec `CMD`: the extras are `$0`/`$1` of the shell and never reach java, but the scan appends them.
- `sh -c "java $JAVA_OPTS -jar ..."` makes `JAVA_OPTS` live, but the scan says it is ignored.
- `--spring.application.json=` in an exec token containing a space is shell-split, so the JSON is unreadable; the scan reports a notice and no exposure.
- Profile group names are matched by canonical spelling; Boot matches the exact spelling, so `prodeu` does not expand for `prod-eu`.
- A placeholder input set in an unevaluated conditional document does not make the dependent property unresolved.
- A Dockerfile `ENV` beneath an unevaluated conditional document is marked unresolved although the OS environment would win; `java --add-modules java.se` is read as a main class; a gap in indexed names (`INCLUDE_1_` without `_0_`) gives a list where Boot fails to start.
- Not examined by any round: lower-case environment names, `envFrom` key collisions, multi-stage Dockerfile targets and `ARG`, `spring.config.import` content, bootstrap and Spring Cloud sources.
